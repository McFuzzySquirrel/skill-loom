# How Skill Loom carries a chain from a project folder to a guarded run {#architecture}

Skill Loom is a local owner process. The CLI and companion skills ask it to author chains, preflight them, and run one chain at a time under review.

- The owner is the only process that writes project state or spawns a harness.
- Every mutating start needs a review digest and explicit confirmations; an authored skill is staged and installed only after a separate approval.
- One active run per profile; tails are bounded and recovery is explicit.
- Harness differences live in adapters, not in routes or runners.

## How does a missing skill become part of the chain? {#gap-panel}

An optional branch closes one gap at a time. Existing steps stay valid, and an instruction-only step remains the fallback. The audit is advisory, not a safety gate; [ADR-0029](source:gap) records the policy.

@steps id=gap-steps
| gap | Record the gap | Name the step role, the sources searched, and why an instruction is not enough. |
| stage | Stage with skill-creator | Scaffold at `<project>/.skill-loom-authored/<name>/`; at most three per chain. |
| audit | Audit with skill-review | Scope the audit to the staged package; the score is advisory. |
| install | Install after approval | Validate, fingerprint, and install without overwrite. |
| resolve | Re-resolve the chain | Refresh the catalog and re-check every step name before packaging. |

## Where is each guard enforced when a run starts? {#run-start-panel}

The control server checks the token and request shape. The orchestrator then re-runs preflight and compares the reviewed digest before it claims the single slot. The owner writes the frozen snapshot before the first process starts.

## What can a run be, and how does it move? {#run-lifecycle-panel span=12}

`starting` covers snapshot and claim. `awaiting-user` is the supervised hand-off after a step ends; automatic runs skip it. Recovery from `interrupted` writes a new `starting` state and never replays a completed step.

## What must be true before a run starts? {#gates}

| Gate | Fails when | Checked by |
| --- | --- | --- |
| Chain shape | The document does not parse or its version is unknown | Chain model |
| Inputs | A required named input has no value | Orchestrator |
| Skills | A named skill is missing, disabled, or ambiguous | Preflight |
| Gap approval | The user did not choose authoring for that step role | Discovery workflow |
| Authored package | The staged package is unsafe or changed after review | Authored-skill helper |
| Harness | The executable is missing or the version is unsupported | Preflight and adapter |
| Trust | The Copilot folder dialog has not been accepted | Trust session service |
| Permissions | Automatic broad permissions were not opted in | Preflight |
| Active run | Another run holds the single slot | Run owner |
| Review digest | The payload changed after you reviewed it | Reviewed-start flow |

## What should I verify before trusting a run? {#checklist}

- [ ] The chain parses and every required input has a value.
- [ ] Preflight resolves every named skill, or reports the missing one.
- [ ] The review digest matches the payload you read.
- [ ] Another run is not holding the active slot.
- [ ] The run record keeps its chain snapshot after you edit the saved chain.
- [ ] A restart shows the run as `interrupted`, not `running`.

## What changed since the November 6 page? {#changes}

That page predates the CLI and skill pivot in `cfbf981`. Its service-first framing still centers the server and editor. The current web surface is the chain editor only; projects, catalogs, discovery, workspaces, and runs are CLI- or skill-driven. Since `343fda3`, ADR-0029 adds the explicit per-gap authoring branch: `scenario-discovery` can hand one gap to `skill-creator`, scope `skill-review` to the staged package, and install only after approval.
