Repo-first skill catalog and chains

Long image

A

Answer

Keep one managed catalog on the container host; let each repo copy only what it needs. The repo owns its chain, and publishing shares a copy.

  1. Clients need a small workflow helper and trusted SSH Podman access, not a Loom server or global catalog.1
  2. Selected skills move into the repo; its chain can run locally in the active session.2
  3. Publishing is explicit and revision-checked, so repo and library copies cannot silently overwrite one another.3

  1. Sync skills source ↗

    Operator updates the host-mounted catalog.

  2. Discover skills ↗

    Remote agent searches the host catalog over SSH Podman.

  3. Copy packages ↗

    Client validates and writes selected packages into its repo.

  4. Author chain ↗

    Repo keeps the editable chain source.

  5. Run locally ↗

    Active session follows the repo chain and local skills.

  6. Publish copy ↗

    Hosted library receives an explicit revision-checked copy.

What is confirmed, and what remains open?

Confirmed direction

Operator syncs the host catalog manually. Repo chains use a new explicit source directory, not legacy .loom/chains/. Skill copies target the repo only and never overwrite an existing package. The repo is canonical; publish one way to the library; run locally in the active session.

Remaining Phase 0 decisions

Choose the exact repo chain directory and document format. Choose where repo-to-library ID and revision mapping lives. Choose an exact catalog identity for selected-skill transfer. Select the first host OS and real Podman-over-tailnet test target.

Execution status

P0 is partially confirmed; its exit gate is open. P1–P6 are not started; no product execution evidence exists yet.
